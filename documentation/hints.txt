BUG pthread_create: Resource temporarily unavailable

https://unix.stackexchange.com/questions/253903/creating-threads-fails-with-resource-temporarily-unavailable-with-4-3-kernel

STATUS mitigated in-tree. The generated container unit carries TasksMax=16384
(modules/containers/libs/systemlib.sh:199), and modules/containers/conf/
srvctl-limits.conf / srvctl-sysctl.conf raise nofile, memlock and the inotify
limits; both are deployed by modules/containers/hooks/update-install-host.sh:21-22
to /etc/security/limits.d/ and /etc/sysctl.d/. Note kernel.pid_max is present but
COMMENTED OUT in srvctl-sysctl.conf -- raise it by hand if a host still runs out.

BUG network unreachable

restart systemd-networkd on the host, .. and on the containers

STATUS half automated. create_network_bridge restarts systemd-networkd on the
host after writing the bridge netdev/network files
(modules/containers/libs/systemlib.sh:259). The container-side restart is NOT
automated: modules/containers/execstartpre.sh:48 has it commented out (systemd
issue 13530) -- do it by hand inside the VE.

BUG container restarts fail

remove --kep-unit

https://github.com/systemd/systemd/issues/2809

STATUS the suggested fix was NOT taken (and the flag is spelled --keep-unit):
it is still on the ExecStart line of srvctl-nspawn@.service, generated at
modules/containers/libs/systemlib.sh:188. srvctl works around systemd#2809
instead by never restarting an nspawn unit -- `sc <VE> restart` is rewritten to
stop + start in modules/containers/hooks/adjust-service.sh:42-48. Do not run
`systemctl restart srvctl-nspawn@<VE>` directly.

## Shipped config: MECH=rimap and FLAGS="-n 0 -O localhost -r" in
## modules/saslauthd/conf/saslauthd.conf, copied to /etc/sysconfig/saslauthd and
## consumed by modules/saslauthd/services/saslauthd.service
## (ExecStart=/usr/sbin/saslauthd -m $SOCKETDIR -a $MECH $FLAGS). rimap means
## SMTP AUTH re-authenticates through the local perdition imap proxy, so it fails
## whenever perdition or the mail container is down.
## Wrappers: `sc testsaslauthd user@ve` reads the mailbox password from
## /srv/<ve>/rootfs/home/<user>/.password (mail.<domain> wins over <domain>) and
## `sc fix-saslauthd` restarts the service. testsaslauthd is operators_only +
## hs_only; fix-saslauthd is operators_only only (no hs_only). Both sudomize,
## so a non-root operator re-execs through sudo.
## Beware: `sc testsaslauthd` echoes the plaintext password to the terminal and
## the process list.
## modules/saslauthd/bin/ still vendors patched 2.1.26-era saslauthd/testsaslauthd
## binaries. They are NO LONGER installed -- update-install-host.sh keeps only the

## STATUS shipped: the main.cf block below is now modules/postfix/conf/ve-main.cf:70-83
