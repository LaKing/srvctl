# letsencrypt — v3 fact sheet (commit 988c38c)

## Purpose
Automates issuance and deployment of Let's Encrypt (ACME) TLS certificates for the
container-hosting domains on a srvctl host. It runs a tiny HTTP server (`acme-server.js`,
port 1028) that answers the ACME `http-01` webroot challenge, drives `certbot`/`letsencrypt
certonly` per container domain (`letsencrypt.js`), then bundles `privkey + fullchain + ca`
into a single `.pem` and deploys it into the datastore (`$SC_DATASTORE_DIR/cert/<domain>.pem`)
and, when a matching container exists, into that container's rootfs
(`/srv/<domain>/rootfs/etc/pki/tls/...`). HAProxy fronts port 80 and forwards the ACME
challenge path to this server.

## Activation  (module-condition.sh logic — when is this module enabled)
`modules/letsencrypt/module-condition.sh` simply `source`s
`$SC_INSTALL_DIR/modules/containers/module-condition.sh` (letsencrypt/module-condition.sh:3),
so the module is enabled exactly when the **containers** module resolves to `true`.
Containers module logic (modules/containers/module-condition.sh):
- `false` if `HOSTNAME == localhost.localdomain`.
- If `$SC_HOSTNET` set or `/etc/srvctl/data` exists: `false` when running inside a container
  (`systemd-detect-virt -c` is `systemd-nspawn` or `lxc`); `true` when
  `/etc/srvctl/hosts.json` exists and contains `"$HOSTNAME"`.
- `true` if `CMD == update-install` and `$ARG` set (install-time).
- otherwise `false`.
Net: enabled on a registered, non-containerized container host (`SC_USE_LETSENCRYPT=true`),
which gates hook and lib loading via `run_hook`/`load_libs`.

## Config & templates (conf/ contents and where they get installed)
No `conf/` directory. Templates/assets are generated inline or vendored:
- `openssl-server-ext.cnf` — OpenSSL v3 extension stanza `[ server ]` (nsCertType=server,
  serverAuth) for OpenVPN-style server certs. **Not referenced** anywhere in this module
  (dead/asset only at this path).
- `letsencrypt-ca.pem` — vendored CA. Installed to `/etc/letsencrypt/ca.pem` by
  `install_acme` (letsencryptlib.sh:43) and read back by `letsencrypt.js` (line 173) to
  append to every deployed bundle. **The cert is `DST Root CA X3`, `notAfter=Sep 30 14:01:15
  2021 GMT` — already expired** (see Bugs).
- `/etc/letsencrypt/cli.ini` — generated by `install_acme` (letsencryptlib.sh:11-16):
  `email = webmaster@$SC_COMPANY_DOMAIN`, `text = True`, `authenticator = webroot`,
  `webroot-path = /var/acme`.
- `/etc/systemd/system/acme-server.service` — generated (letsencryptlib.sh:22-38): runs
  `/bin/node .../apps/acme-server.js` as `acme:acme`, `Restart=always RestartSec=3`,
  `WantedBy=multi-user.target`. Old copy at `/lib/systemd/system/acme-server.service` is
  `rm -fr`'d (line 41, marked TODO remove).

## State touched (host paths, container paths, systemd units, datastore keys, network)
Host paths:
- `/etc/letsencrypt/` — `cli.ini`, `ca.pem`, `live/<lineage>/` (certbot output), `live` dir created.
- `/var/acme/` — ACME webroot (owned by `acme:acme`); challenge files under
  `/var/acme/.well-known/acme-challenge/`.
- `$SC_DATASTORE_DIR/cert/` — deployed bundles `<domain>.pem` (privkey+fullchain+ca).
- `/etc/srvctl/cert/<domain>/<domain>.pem` — **read** for wildcard detection (owned by the
  `certificates` module; consistent with wildcardcertlib.sh).
- `/srv/<name>/letsencrypt<name>.log` and `/srv/<name>/letsencrypt-www.<name>.log` — certbot
  stdout append logs (asymmetric names, see Bugs).
- `/lib/systemd/system/acme-server.service` — removed.

Container paths (when `/srv/<domain>/rootfs/etc/pki/tls/{private,certs}` both exist):
- `.../private/localhost.key` (privkey)
- `.../certs/localhost.crt` (fullchain + ca)
- `.../certs/<domain>.pem` and `.../certs/localhost.pem` (full bundle)

systemd units: `acme-server.service` (enable/start/status).

User/uid: creates system user `acme`, uid `528`.

Network: listens `0.0.0.0:1028` HTTP (acme-server.js:36); reached by HAProxy backend
`server letsencrypt 127.0.0.1:1028` for acl `path_beg /.well-known/acme-challenge/`
(haproxy.js:149,425). Outbound HTTPS to the ACME CA via certbot.

datastore keys: reads `containers`, `hosts` (JSON via datastore/lib.js); uses
`containers[name].dns[...]` (populated by `dns/dns-scan.js`), `.aliases`, `.altnames`,
`.subdomains`, `hosts[HOSTNAME].host_ip`.

## Bugs & smells
(severity file:line — defect and concrete harm; only real findings)

- **HIGH** `letsencrypt-ca.pem` (whole file) / used at letsencryptlib.sh:43, letsencrypt.js:173,181,195 — the vendored CA is `DST Root CA X3` with `notAfter=Sep 30 2021` (expired). It is concatenated into every deployed bundle (`pem = privkey + fullchain + ca`) and into container `localhost.crt`. Appending an expired root to the chain is at best redundant (certbot's `fullchain.pem` already carries the correct ISRG chain) and at worst causes TLS validation failures / chain-cleanup warnings on strict clients. Concrete harm: deployed certs ship an expired root in the presented chain.
- **MEDIUM** letsencrypt.js:298 — operator-precedence bug in the nameserver hint string: `(containers[name].dns[domain].NS[0] || "?" + " " + containers[name].dns[domain].NS[1] || "?")`. `+` binds tighter than `||`, so when `NS[0]` is truthy only `NS[0]` is shown, and the intended `(NS[0]||"?") + " " + (NS[1]||"?")` never happens. Concrete harm: the "no A record" diagnostic prints garbled/incomplete nameserver info, hindering debugging.
- **MEDIUM** acme-server.js:15 — `fs.access(file, fs.R_OK, cb)`. `fs.R_OK` is a long-deprecated alias (real constant is `fs.constants.R_OK`); on Node versions where it is `undefined`, `fs.access` falls back to `F_OK`, so it checks existence rather than readability. Concrete harm: an existing-but-unreadable challenge file would be read and then error inside `readFile` ("INVALID DATA") instead of the intended "CANNOT READ" path; brittle across Node versions.
- **LOW** letsencryptlib.sh:19 — `useradd -r -u 528 ... acme` is not guarded for an existing user and not wrapped in `run`/`eyif`; on re-install `useradd` fails ("user already exists") with an unmanaged stderr error. Non-fatal but noisy/misleading.
- **LOW** letsencrypt.js:222-236 — asymmetric log filenames: non-www runs append to `/srv/<name>/letsencrypt<name>.log` (no separator, e.g. `letsencryptfoo.hu.log`) while www runs use `/srv/<name>/letsencrypt-www.<name>.log`. Same container's runs scatter across differently-named files, complicating log review.
- **LOW** letsencrypt.js:127-138 — `check_checkend` prints the raw openssl command via `ntc(...)` on **every** call (line 131) regardless of outcome, and uses `return` inside a `finally` block (line 137) which swallows control flow. Works, but produces constant yellow noise and is a lint-flagged pattern.
- **LOW (dead code/smell)** letsencrypt.js:31,34,26,50-53 — `SC_UID0`, `localhost`, `SC_CONTAINERS_DATA_FILE`, and `return_error()`/`output()`/`return_value()` are declared but unused; `openssl-server-ext.cnf` is never referenced by this module. Maintenance clutter.
- **LOW** letsencrypt.js:167-202 — best-effort by design: `letsencrypt_deploy` early-`return err(...)` on any missing input and the script still ends `process.exitCode = 0`; per-domain failures are invisible to the caller's exit status.

  (acme-server.js:10, length check `> 28`).

  `/var/acme/.well-known/acme-challenge/`) — letsencryptlib.sh:15,18-20, acme-server.js:13.

  `text = True`, `authenticator = webroot`, `webroot-path = /var/acme`) — letsencryptlib.sh:11-16.

- Container deploy targets and their contents: `.../private/localhost.key` = privkey;

  `.../certs/localhost.pem` = full bundle (letsencrypt.js:190-198) — only when both
  `/srv/<domain>/rootfs/etc/pki/tls/private` and `.../certs` exist.
- certbot invocation flags exactly: `letsencrypt certonly --non-interactive --agree-tos
  --keep-until-expiring --expand --webroot --webroot-path /var/acme/ -d <domain> [-d www.<domain>]`
  (letsencrypt.js:218-236).
- Skip rules in `main()`: skip names starting `mail.`; process containers with `subdomains`
  via `check_container`; skip names ending `.devel`/`-devel`/`.local`/`-local`; skip names

- Wildcard detection path **`/etc/srvctl/cert/<domain>/<domain>.pem`** and www→base stripping
  logic (letsencrypt.js:62,71-76) — must stay in sync with the `certificates` module.
- Expiry window: `openssl x509 -checkend 604800` (7 days) (letsencrypt.js:131-132).
- Guard exit code **`exit 4`** in hooks/update-install-host.sh:5; JS process exit codes

- lineage-matching regex in `get_le_dir` — base name plus `-NNNN` suffixes, newest `notAfter`
  wins (letsencrypt.js:99-124); certbot creates `<domain>-0001` style lineages.
- Log file paths (both variants) as listed under State (rewrite must keep or consciously
  migrate consumers).

## v4 notes
- The whole cert-request/deploy engine (`letsencrypt.js`) is already JS and should become a
  proper `.mjs` module; it duplicates helper wiring (`lablib.js` require boilerplate,
  ad-hoc `out/return_value/output` functions) shared with other JS modules — consolidate on a
  single lablib/datastore import surface.
- `letsencrypt_main` (bashlib.sh) and `regenerate_letsencrypt` (letsencryptlib.sh) are trivial
  bash shims around the node call; collapse into the module's install/regenerate entrypoints.
- Drop the vendored expired `letsencrypt-ca.pem`: modern certbot `fullchain.pem` already
  provides the correct chain; either stop appending a static root or vendor the current ISRG
  root(s) — the current file is a latent TLS hazard.
- Remove the dead `openssl-server-ext.cnf` from this module (belongs to the OpenVPN/CA path)
  and the unused JS symbols.
- `acme-server.js` is a 30-line static-file responder; in v4 it could be folded into the
  existing datastore/haproxy node runtime or replaced by certbot's built-in `--standalone`/
  a webroot the main HTTP layer already serves, removing a bespoke always-on service +
  systemd unit + dedicated uid.
- Fix `fs.R_OK`→`fs.constants.R_OK`, the NS-hint precedence bug, and normalize the log
  filenames while porting.
- Consider surfacing per-domain success/failure via a non-zero aggregate exit code so callers
  (haproxy regenerate, cron) can detect issuance failures.
