# opendkim — v3 fact sheet (commit 988c38c)

## Purpose
Provides DKIM signing (and verification) for all outgoing farm mail. At install time it installs `opendkim`/`opendkim-tools` and writes `/etc/opendkim.conf` (milter on `inet:8891@127.0.0.1`, consumed by the postfix module's host `main.cf`). At every `sc regenerate` it runs `opendkim.js`, which for every non-devel/non-local container domain: generates an RSA key with `opendkim-genkey` into `/srv/<domain>/opendkim/` if missing, syncs the private key into the shared datastore (`$SC_DATASTORE_DIR/opendkim/<domain>/`), publishes the public key into `containers.json` as `dkim-<selector>-domainkey` (consumed by the named module for DNS TXT records), and rebuilds `TrustedHosts`/`KeyTable`/`SigningTable`. The bash lib then mirrors the datastore folder to `/var/opendkim` (the runtime location referenced by `/etc/opendkim.conf`) and restarts `opendkim.service` when anything changed.

## Activation
`module-condition.sh:4` simply sources `modules/containers/module-condition.sh`, so `SC_USE_OPENDKIM` is exactly the containers-module condition: false on `localhost.localdomain` or inside a container (`systemd-detect-virt -c` is `systemd-nspawn`/`lxc`); true when (`SC_HOSTNET` set or `/etc/srvctl/data` exists) and `$HOSTNAME` appears quoted in `/etc/srvctl/hosts.json`; also true during `sc update-install <arg>`. Evaluated in a subshell by `commonlib.sh:436` and cached in `modules.conf`.

## Config & templates
No `conf/` directory. Single inline template: `/etc/opendkim.conf` heredoc in `hooks/update-install-host.sh:9-42`, installed on the host during `sc update-install` (overwrites unconditionally; header comment contains the typo "onemdkim.conf", line 10).

## State touched
- Host files: `/etc/opendkim.conf`; `/var/opendkim/{TrustedHosts,KeyTable,SigningTable}` and `/var/opendkim/<domain>/<selector>.private` (owner `opendkim:opendkim`, dirs 750, files 640); `/etc/srvctl/system/opendkim.service` symlink (via `add_service`).
- Datastore: `$SC_DATASTORE_DIR/opendkim/` (dir chmod 000, root-only; per-domain `<selector>.private` plus the three tables — on clusters this dir may live on the shared gluster datastore, which is how keys reach other hosts); `containers.json` keys `dkim-default-domainkey` / `dkim-mail-domainkey` (value includes leading `p=`); `containers.json` is fully rewritten on every regenerate.
- Container-adjacent: `/srv/<domain>/opendkim/{default|mail}.{private,txt}` created root-owned inside the container's `/srv` area.
- systemd: `opendkim.service` (enable/restart/status).
- Network: opendkim milter listens on `127.0.0.1:8891` (config only; postfix on the host connects to it). TrustedHosts grants internal-host status to `127.0.0.1`, `::1`, all of `10.0.0.0/8`, and every hosted domain (`opendkim.js:73-75,110`).

## Bugs & smells
- **MEDIUM** `opendkim.js:105` — `txt.split('"')[3]` assumes the public key is a single quoted chunk in `opendkim-genkey`'s `.txt` output. Keys longer than 255 bytes (e.g., anything generated with `-b 2048`, or a future opendkim-tools default change) are emitted as multiple quoted strings; only the first chunk is stored, so `named` publishes a truncated `p=` and DKIM validation fails for that domain with no error anywhere. Corollary: if the `.txt` layout differs, `[3]` is `undefined` and the assignment at `opendkim.js:106` silently deletes a previously valid `dkim-*-domainkey` from `containers.json` (`JSON.stringify` drops `undefined`), removing the DNS record at the next named regenerate.
- **MEDIUM** `opendkim.js:130` — `containers.json` is rewritten wholesale from an in-memory snapshot loaded at process start, without locking or change detection. A concurrent srvctl operation that modifies `containers.json` between this script's load and its exit (e.g., `add-ve` on another terminal, or a datastore sync landing mid-run) has its change silently reverted; the file is also dirtied on every regenerate even when nothing changed, churning the shared datastore.
- **LOW** `hooks/update-install-host.sh:44-46` — `regenerate_opendkim` is commented out but `add_service opendkim` enables and restarts the daemon while `/etc/opendkim.conf` points at `/var/opendkim/{KeyTable,SigningTable,TrustedHosts}` which do not exist on a fresh host; `opendkim.service` fails to start until the first `sc regenerate`, and outgoing mail is meanwhile unsigned (postfix `milter_default_action accept`, `modules/postfix/conf/hs-main.cf:84`).
- **LOW** `opendkim.js:90` — the domain name is interpolated unescaped into a root `execSync` shell command; a `containers.json` key containing `"` or `$(...)` executes arbitrary shell as root. Domains normally come from validated `add-ve` input, so this needs a corrupted or attacker-writable datastore, but it is an unsanitized root-context injection.
- **LOW** `hooks/version.sh:3` — dead hook: nothing in the tree runs `run_hook version` (same for named/perdition/postfix/saslauthd), so `sc version` never reports opendkim. Harm limited to a misleadingly present file.
- **LOW** `libs/opendkimlib.sh:19` — unquoted glob `chmod 640 /var/opendkim/*/*` passes the literal pattern to chmod when no domain directories exist (fresh cluster), printing a chmod error; execution continues (no `set -e`), noise only.
- Smells: `opendkim.js:5-11,22,62-67` — bulk of the datastore-js boilerplate is dead here (`ntc`, `get`, `run`, `rok`, `CMD`, `hosts`, `users`, `resellers`, `user`, `container`, `out`, `return_value`, `return_error`, `output`, the `exitCode=99` ceremony at 34-38); `opendkim.js:96` uses the reserved word `private` as a variable (sloppy-mode only); `libs/systemdlib.sh:9` leaks a non-local global named `test`; `opendkim.js:111` KeyTable may reference `/var/opendkim/<domain>/<sel>.private` files that are not yet in the datastore (container added on another host before its regenerate), leaving opendkim with entries whose key file is missing until the owning host regenerates and the datastore syncs.

## Polish risks
- Datastore/runtime layout: `$SC_DATASTORE_DIR/opendkim/{TrustedHosts,KeyTable,SigningTable}` + `<domain>/<selector>.private` (`opendkim.js:97-101,127-129`), mirrored verbatim to `/var/opendkim` (`libs/opendkimlib.sh:16`); `/etc/opendkim.conf` references exactly `/var/opendkim/KeyTable`, `refile:/var/opendkim/SigningTable`, `refile:/var/opendkim/TrustedHosts` (`hooks/update-install-host.sh:37-40`).
- Table line formats: KeyTable `<sel>._domainkey.<domain> <domain>:<sel>:/var/opendkim/<domain>/<sel>.private` (`opendkim.js:111`); SigningTable `*@<domain> <sel>._domainkey.<domain>` (`opendkim.js:112`); TrustedHosts begins `127.0.0.1`, `::1`, `10.0.0.0/8` then every domain (`opendkim.js:73-75,110`).
- Selector rule: `mail` iff domain starts with `mail.`, else `default` (`opendkim.js:78-79`) — key filenames, KeyTable/SigningTable entries, datastore keys (`dkim-mail-domainkey` vs `dkim-default-domainkey`) and named.js zone records (`named.js:213-236`) all depend on it.
- Datastore values keep the literal `p=` prefix (`opendkim.js:105-106`); `named.js:211-236` prepends only `"v=DKIM1; k=rsa;"` — stripping the prefix breaks every published DKIM record.
- Exclusion rule: domains ending `.devel`, `-devel`, `.local`, `-local` are skipped entirely (`opendkim.js:117`).
- Key reuse: keys are generated only when `/srv/<domain>/opendkim/<sel>.private` is absent (`opendkim.js:86`); a rewrite must never regenerate existing keys (DNS holds the public half). Datastore copy is overwritten from `/srv` every run (`opendkim.js:101`), i.e. `/srv` is authoritative on the owning host.
- `containers.json` written as `JSON.stringify(containers, null, 2)` (`opendkim.js:130`) — changing serialization churns the shared datastore.
- Permissions: datastore opendkim dir mode 000 (`libs/opendkimlib.sh:8`); `/var/opendkim` owner `opendkim:opendkim`, dirs 750, key/table files 640 (`libs/opendkimlib.sh:17-22`, `libs/systemdlib.sh:5`).
- `/etc/opendkim.conf` semantics: `Mode vs`, `Socket inet:8891@127.0.0.1` (must match `modules/postfix/conf/hs-main.cf:82`), `UserID opendkim:opendkim`, `MinimumKeyBits 1024`, `Canonicalization relaxed/relaxed` (`hooks/update-install-host.sh:16-40`).
- Exit/error contract: node exits 0 on success; failure aborts the whole srvctl run via `exif "OPENDKIM-ERROR cfg ..."` passing node's exit code through (`libs/bashlib.sh:9`).
- Output strings scripts/operators may match: `regenerate opendkim` (`opendkimlib.sh:5`), `Updating $HOSTNAME opendkim runtime configuration` (`opendkimlib.sh:14`), `Configuration for opendkim is up-to-date, opendkim.service running` / `Configuration for opendkim is up-to-date.` (`opendkimlib.sh:29,31`), `opendkim.service is not running!` (`opendkimlib.sh:32`), `restarted opendkim.service` / `opendkim restart FAILED!` (`systemdlib.sh:13,17`), `Wrote OpenDKIM TrustedHosts, KeyTable, SigningTable to <dir>` (`opendkim.js:131`), the echoed `opendkim-genkey -D "..." -d "..." -s "..."` command line (`opendkim.js:89`).
- systemd side effects: `opendkim.service` enabled + restarted, symlink in `/etc/srvctl/system/` (`add_service`, `hooks/update-install-host.sh:46`); restart only happens when the diff detects changes (`opendkimlib.sh:12`), otherwise a running service is left untouched.

## v4 notes
- `opendkim.js` is a copy of the shared datastore-js boilerplate with ~60% dead code; in v4 this collapses into a small `.mjs` that imports a real datastore API (load/save with locking and dirty-checking) instead of raw `fs.writeFileSync` on `containers.json` — that alone fixes the lost-update race and the pointless rewrite churn.
- Replace the `txt.split('"')[3]` parse: derive the public key directly from the private key (e.g., crypto API or `openssl rsa -pubout`) or join all quoted `p=` chunks; store the raw base64 (and let the DNS layer add `p=`), with a compatibility shim for existing datastore values.
- The bash trio (`opendkim_main`/`regenerate_opendkim`/`restart_opendkim`) is the standard module pattern (same shape as named: generate → diff → copy → restart); a v4 module contract could reduce this to declarative "managed files + service" so the diff/copy/chmod/restart dance is shared code, not per-module bash.
- `chmod 000` + root-only copy is an ad-hoc secret store; v4 should have one blessed place/permission scheme for private key material in the datastore (also used by ca/letsencrypt modules).
- The `/etc/opendkim.conf` heredoc belongs in a `conf/` template (every other config-writing module also mixes templates into hook code — recurring duplication theme).
- Dead `hooks/version.sh` pattern repeats across five modules; either wire a real `version` hook into the `version` command or drop the files.
- Consider generating KeyTable entries only for domains whose key file actually exists in the datastore, to avoid opendkim referencing missing keys between cluster syncs.
