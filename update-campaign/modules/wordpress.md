# module wordpress — v3 fact sheet (commit 988c38c)

## Purpose
Turns a fresh srvctl container into a self-contained WordPress microsite: one command (`install-wordpress`, run as root *inside* the container) installs PHP + MariaDB + Apache config, downloads the latest upstream WordPress into `/var/www/html`, generates `wp-config.php` with fresh DB credentials and salts, performs a headless `wp_install()` (site title = container hostname, user `admin`, generated password), and enables `httpd`. A standalone maintenance script can reset the WP admin password from the saved `.admin` file. Consumed by `modules/containers/commands/recreate-ve.sh:61` (`ssh "$C" 'sc install-wordpress'`) when rebuilding wordpress-type containers.

## Activation
`module-condition.sh:1-12`: sets `container=$HOSTNAME`; if the hostname starts with the literal 5 chars `mail.` it echoes `false`; otherwise it sources `modules/ve/module-condition.sh`, which echoes `true` iff `systemd-detect-virt -c` reports `systemd-nspawn` or `lxc` (`modules/ve/module-condition.sh:3-12`). Net effect: enabled inside **every container except `mail.*` containers**, never on hosts. Evaluated in a subshell by `test_srvctl_modules` (`commonlib.sh:436`), cached as `export SC_USE_WORDPRESS=<bool>` in `modules.conf` (`commonlib.sh:448`). Requires `$SC_INSTALL_DIR` to be set (it is, from init) to find the ve condition.

## Bugs & smells
- **high** `scripts/restore-wordpress-password.sh:61` — `mysql "$SC_MDA" -e "use $1; 'show tables';"`: the quoted `'show tables'` is a bare string literal statement → MySQL syntax error (1064) → the `else` branch exits **every run**, so the script can never reach the password UPDATE at :79. The one recovery tool for lost admin passwords is entirely non-functional.
- **high** `scripts/restore-wordpress-password.sh:29,32,35,47,61,69,79,87` — `$SC_MDA` is passed quoted as a *single* argument; the fallback `SC_MDA="-u root -p"` (:32) becomes one unknown-option token, so without `/etc/mysqldump.conf` every mysql call fails at the connection check (and `-p` would prompt interactively anyway). Restore is impossible on any container lacking the dump conf.
- **medium** `scripts/restore-wordpress-password.sh:9,41,52,58,66,74,84` — every failure path is a bare `exit` immediately after a successful `echo`, so the script **exits 0 on failure**; callers/automation cannot detect that nothing was restored.
- **medium** `commands/install-wordpress.sh:55` — `run curl https://wordpress.org/latest.zip > "$wd"/latest.zip`: `run` (`lablib.sh:93-110`) echoes the ANSI-colored command banner on stdout *before* executing, so the banner is prepended inside `latest.zip` (unzip only tolerates it as "extra bytes" junk). Worse, on curl failure nothing aborts — `run`'s `eyif` reads `$?` of the preceding `[[ ]]` test (always 0, `lablib.sh:108-111`+`:150`) so the failure isn't even warned — and the script proceeds through DB creation, writes a wp-config for an empty webroot, and still prints the success message at :155. Network hiccup ⇒ silently broken site reported as installed.
- **medium** `commands/install-wordpress.sh:130` + `:114` — `$URI` is defined nowhere in the repo, so `WP_SITEURL` is `http://$HOSTNAME/` (scheme **http**), while `FORCE_SSL_ADMIN` is `true` and the final message advertises `https://…/wp-admin`. Behind srvctl's TLS-terminating reverse proxy (backend sees plain http; wp-config has no `HTTP_X_FORWARDED_PROTO` handling), `/wp-admin` over https redirect-loops and front-end links are generated as `http://`.
- **medium** `commands/install-wordpress.sh:139,150-151,160` — `wp-install.php`, containing the admin password in plaintext PHP source, is never deleted from the webroot; `.admin` (plaintext password) and `wp-config.php` (DB creds) are `chown -R apache:apache`'d at :160 *after* the `chmod 000`, so any compromised apache-uid process owns them and can `chmod +r` `.admin` or rewrite `wp-config.php`. Password/credential exposure to the web workload, forever.
- **low** `commands/install-wordpress.sh:8` (whole file) — missing the conventional `[[ $SRVCTL ]] || exit 10` guard (CLAUDE.md); running the file directly with bash skips undefined helpers (`root_only`, `run`, `sc_install` → "command not found") but still executes the raw `cat >`/`chown` lines, clobbering `/etc/httpd/conf.d/*` and `wp-config.php` with empty `$db_usr`/`$db_pwd`.
- **low** `commands/install-wordpress.sh:56` — `unzip` without `-o`, stdout redirected to a log: if `/root/wordpress` survives a previous aborted run, unzip prompts for overwrite invisibly (tty run appears hung; non-tty gets EOF errors).
- **low** `commands/install-wordpress.sh:51,64,76` — DB-name correctness for hyphenated hostnames depends on `add_mariadb_db` *reassigning the caller's global* `db_name` to the sanitized value (`mariadblib.sh:97-103`); accidental cross-module coupling a rewrite could easily break (wp-config would then reference a nonexistent DB).
- **low** `scripts/restore-wordpress-password.sh:15-17,77` — announces and echoes the plaintext password (and would-be hash) to stdout/logs; `HASH` (:16) is dead code and wrong anyway (`echo` includes a trailing newline in the md5).
- smell: `commands/install-wordpress.sh:11-13` installs the Fedora `wordpress` RPM *and* the upstream zip (double install; RPM only useful for dependency pull-in, its apache conf is deleted at :45-48); comment `## lock to 8.0.11 for now` (:10) no longer matches reality (documentation.md:1241 still claims PHP 8.0.11); `err $?` (:146) reports only a bare exit code; `wp-includes/wp-db.php` require (:136) is a deprecated stub since WP 6.1.

## Polish risks
- Help block strings, verbatim (`commands/install-wordpress.sh:3-6`): `## @@@ install-wordpress`, `## @en Run scripts that install wordpress and it's basic dependencies.` (typo included), `## &en Install the wordpress dependencies.` — rendered by help.
- Output lines users/scripts see: `msg` texts at :16,30,44,53,66,141,144 and especially `:155` `Wordpress @ https://$HOSTNAME/wp-admin admin:$password` (operators copy the password from this line); `root_only` prints `SC_UID0 true` (`authlib.sh:6`); non-root exit code **44** (`authlib.sh:10`).
- Generated file paths + markers other code/operators rely on: `/var/www/html/wp-config.php` (rsync'd by `recreate-ve.sh:69`), `/var/www/html/wp-content` (`recreate-ve.sh:68`), `/var/www/html/.admin` mode 000 (read by `scripts/restore-wordpress-password.sh:6,12`), `/var/www/html/wp-install.php`, `/etc/httpd/conf.d/wp-permalink.conf`, `/etc/httpd/conf.d/logging-behind-reverse-proxy.conf`, deletion of `/etc/httpd/conf.d/wordpress.conf` (:45-48), deletion of `/var/www/html/index.html` (:153), `## srvctl generated` header comments (:18,32).
- Install semantics: DB name `<first-hostname-label>_wp` sanitized `.`/`-`→`_` (:51 + `mariadblib.sh:100-103`) and its `/etc/mariadb-<db>.conf` side effect; `table_prefix 'wp_'` (:107, restore script queries `wp_users`); admin username `admin`, email `root@localhost`, blog title `$HOSTNAME` (:137); `FORCE_SSL_ADMIN true` (:114); `WP_DEBUG false`; DB_HOST `localhost`; `chown -R apache:apache /var/www/html` ownership; `combined` LogFormat redefinition consumed by any log tooling (:39).
- Activation contract: enabled in every non-`mail.*` container, cached as `SC_USE_WORDPRESS` in `modules.conf`; `recreate-ve.sh:61` invokes literally `sc install-wordpress` over ssh — the command name must not change.
- Restore script's documented invocation path `/usr/local/share/srvctl/modules/wordpress/scripts/restore-wordpress-password.sh` (:4, also documentation.md:1249).

## v4 notes
- Natural `.mjs` candidate: a single `installWordpress()` flow — templated wp-config (use one heredoc/template instead of 50 `echo`s :73-122), proper fetch with checksum + abort-on-failure, salts from `crypto.randomBytes` (replaces the ad-hoc `get_randomstr` :68-70), and structured JSON result (site URL, db, password) instead of a parse-me `msg` line.
- Fold the restore script into a real command (`restore-wordpress-password`) with the module's help metadata, correct mysql arg handling (array/defaults-file), non-zero exits — today it is dead weight (see Bugs) so v4 can rewrite it freely except for the `.admin` contract.
- Kill the double install (RPM + upstream zip): install only PHP deps via dnf, or only the RPM. Consider `wp-cli` for install/password-reset instead of hand-rolled `wp-install.php` + SQL.
- Replace the global-variable contract with `add_mariadb_db` (`db_usr`/`db_pwd`/`db_name` leakage) with an explicit return object; same cleanup is flagged in the mariadb fact sheet.
- Delete `wp-install.php` after use; store `.admin` under `/root` not the webroot; add reverse-proxy `X-Forwarded-Proto` snippet to wp-config and make `WP_SITEURL` https.
- The `mail.*` exclusion in module-condition duplicates a naming convention other modules also test; v4 should expose container *type/role* (e.g. from datastore) instead of hostname-prefix sniffing.
